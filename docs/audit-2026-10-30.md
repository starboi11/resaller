# Audit 2026-10-30 — API correctness, access control, checkout integrity

Scope: `apps/api` (all modules), `packages/config`, and an end-to-end run of the
stack on localhost. The buyer and admin front ends were exercised through the
browser but their source was **not** reviewed.

Verification for every fix below: `pnpm --filter @resaller/api test` (113 passing,
including the PostgreSQL integration suites with `RUN_DB_TESTS=1`), `tsc --noEmit`
clean across the API and the three shared packages, `pnpm security:secrets` clean,
plus a manual end-to-end purchase through the running web app.

---

## Fixed

### 1. Checkout sold from closed stores (high)

`checkout()` never re-checked purchasability. `addCartItem()` validates
`listing.status` and `store.status` at the moment an item is added, but anything
can change between that moment and checkout, and `vacationMode` was not checked
anywhere on the ordering path — only in `commerce.service.ts` for display
(`purchasable`).

Reproduced against the original code on a running server: with the store left
`ACTIVE` but `vacationMode = true`, `POST /checkout` returned **201**, created
order `ALC-…` for 100 000 UZS and reserved stock (25 → 23 available, 2 reserved).
A suspended or unpublished listing behaved the same way.

`checkout()` now re-validates store status, vacation mode, listing status and
`deletedAt` **inside** the serializable transaction, before any stock is
reserved. Verified: each case returns 409 with inventory untouched.

Files: `apps/api/src/operations/operations.service.ts`,
tests in `apps/api/src/operations/checkout-guards.test.ts`.

### 2. State-changing requests without an Origin were allowed (medium)

`isOriginAllowed()` returned `true` whenever the `Origin` header was absent, for
every method. Cookie authentication plus `SameSite=Lax` made this hard to abuse,
but it was the only CSRF layer. Unsafe methods now require a trusted Origin;
safe methods are unchanged.

Every mutating call in `apps/web` is client-side with `credentials: 'include'`,
so browsers always send Origin and no application behaviour changed. The four
direct `page.request.*` calls in `e2e/media-limits.spec.ts` now send an explicit
Origin, because Playwright's `APIRequestContext` does not add one.

Files: `apps/api/src/common/origin-policy.ts`, `apps/api/src/main.ts`,
`e2e/media-limits.spec.ts`.

### 3. Every error message was replaced with "Request failed" (medium)

`HttpExceptionFilter` masked the message of every non-500 response. The domain's
deliberately user-facing messages — "Store is in vacation mode", "Stock changed;
review cart", "Discount exceeds subtotal" — never reached the caller, so 400,
403, 404 and 409 were indistinguishable. A buyer whose checkout failed had no
way to tell a sold-out item from a closed store.

Messages from `HttpException` (which the code writes for the caller) now pass
through, including `ValidationPipe`'s per-field list. Anything that is not an
`HttpException`, and every 500, stays masked so internal detail cannot leak.

Note: these messages are English while the product is Uzbek. Returning a stable
error code for the front end to localise is the proper follow-up.

Files: `apps/api/src/common/http-exception.filter.ts` and its new test.

### 4. No `P2002` / `P2034` handling outside Seller Center (medium)

`seller-center.service.ts` handled both; `operations.service.ts` handled
neither. Two concurrent submissions of one `idempotencyKey` hit the unique
constraint and returned **500** instead of replaying the winning checkout, and a
serialization conflict — an ordinary outcome when two buyers race for the same
stock — also surfaced as 500.

Added `apps/api/src/common/prisma-errors.ts`; all six serializable transactions
in `operations.service.ts` now map `P2034` to 409, and `checkout()` additionally
replays the winner's checkout on `P2002`. The three inline error-code checks in
Seller Center were moved onto the same helper.

### 5. Payment record had no state machine and no optimistic lock (medium)

`updatePaymentRecord()` read the order outside its transaction and then wrote
unconditionally — no isolation level, no status guard. Concurrent writes were
silently lost and the audit log's `from` value could be wrong. `REFUNDED → PAID`
was permitted, which would quietly return a refunded order to revenue, since
`finance()` excludes refunded orders from `externalRevenueMinor`.

Now runs inside a serializable transaction with an `updateMany` status guard and
a state machine. A seller may still correct a collection mistake freely between
`UNPAID`, `PARTIAL` and `PAID`; `REFUNDED` is terminal.

A first attempt at this machine also blocked `UNPAID → REFUNDED`. The PostgreSQL
integration suite caught it: a delivered order counts as revenue whether or not
it was marked `PAID`, so a cash-on-delivery refund has to be reachable straight
from `UNPAID`.

Files: `apps/api/src/seller-center/seller-center.service.ts`,
tests in `apps/api/src/seller-center/payment-record.test.ts`.

### 6. `.env.example` could not start the API (medium)

`S3_ENDPOINT`, `S3_BUCKET`, `S3_PRIVATE_BUCKET`, `S3_ACCESS_KEY_ID` and
`S3_SECRET_ACCESS_KEY` used `z.string().min(1).optional()`, which rejects the
empty value `.env.example` ships. Following the README literally produced a
startup failure. They now use the `optionalSecret` preprocessor already defined
for exactly this purpose; `superRefine` still requires them when
`MEDIA_STORAGE_DRIVER` is `s3`.

Files: `packages/config/src/index.ts` and its test.

### 7. Encryption key could not be rotated (low)

Ciphertext carried no key generation, so changing `DATA_ENCRYPTION_KEY` would
have made every stored phone number and address unreadable and split the
customer base on `phoneHash`. Ciphertext is now prefixed `v1.`, and
`DATA_ENCRYPTION_KEY_PREVIOUS` is accepted for reads during a rotation. Rows
written before the prefix existed still decrypt.

The runbook still needs the operational procedure written down.

Files: `apps/api/src/notifications/endpoint-crypto.service.ts`,
`packages/config/src/index.ts`.

### 8. Smaller fixes

- Duplicate phone on `updateCustomer` raised an unhandled `P2002` (500); now 409.
- `displayId` used `Math.random()` against a unique column; now `randomBytes`.
- `adjustStock` reported "Insufficient available stock" when the variant simply
  had no `Inventory` row.
- The idempotent replay of `createExternalOrder` returned a different response
  shape from the original create.
- `checkout` accepts an optional `expectedTotalMinor` per store and refuses to
  charge a different total. **The web app does not send it yet** — wiring it up
  is the remaining half of this fix.
- `dashboard` resolved the store four times (~18 queries). `storeFor` now takes
  several capabilities at once and the read models take a store id, so the
  dashboard requires `analytics.view` + `finance.view` + `orders.view`
  explicitly. Confirmed on a running server that no existing role's access
  changed.

## Checked, no issue found

- **Broken access control.** Probed on a running server with an owner, an
  unrelated user and an `ORDER_OPERATOR`. Anonymous → 401; unrelated user → 403
  on dashboard, orders, inventory, customers, finance and assistant-context;
  unknown store → 404; operator → 200 on its capabilities and 403 on finance.
  Every Seller Center method goes through `storeFor()`, and customers and orders
  are fetched with a `storeId` predicate, so no IDOR was found.
- `PasswordService` — scrypt N=32768, length-checked `timingSafeEqual`.
- `couponDiscount` — minimum, cap and subtotal clamp all correct in `BigInt`.
- `OrderTimeoutService` — idempotent across replicas.
- Security headers and cookie flags.

## Corrected finding

An earlier draft of this audit claimed that the `onRequest` origin hook not
returning its reply let the route handler run anyway. Testing the original code
on Fastify 5.12.5 disproved it: the blocked request returned 403 and wrote
nothing. `return reply` is still the documented form and is kept, but it was not
a security defect.

## Not reviewed

`apps/web` and `apps/admin` source, the `media` module (upload, ClamAV), `trust`,
`support`, `admin`, and most of `commerce.service.ts`.

## Launch assessment

The platform does not collect payment. `PLATFORM_BUSINESS_RULES` sets
`commissionBasisPoints: 0` with `paymentCollection`, `escrow` and `settlement`
all `DEFERRED`, no gateway is integrated, and the cart tells the buyer in plain
Uzbek that payment is arranged with the seller off-platform. `paymentStatus` is
seller-recorded and the code says so (`verifiedSettlement: false`). Until a
gateway is integrated the platform cannot take commission, hold funds, or back
its buyer-protection claims.

Recommended: a closed beta of the Seller Center with a handful of known sellers
now, and a public launch only after payment integration, error-message
localisation and a front-end review.
